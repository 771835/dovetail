# DFP 603: 编译缓存与增量编译

## 提案信息

**作者**: 771835 <2790834181@qq.com>  
**状态**: Draft  
**创建日期**: 2026-02-03  
**最新更新**: 2026-08-10

## 设计目标

为 Dovetail 编译器引入分层编译缓存与增量编译能力，通过在 **AST 层** 和 **IR 层** 分别缓存中间产物，
避免重复编译未修改的文件，提升大型项目的编译速度。

## 动机

### 问题背景

1. **全量重新编译**  
   当前每次编译都从头开始解析、生成 IR、优化，即使只修改了一个文件。

2. **大型项目编译慢**  
   包含多个 `include` 文件的项目，每次编译都需要重新处理所有依赖， 而 `IncludeManager` 已经具备完整的依赖图追踪能力，尚未用于缓存失效判断。

3. **已有序列化基础未充分利用**  
   `IRSymbolSerializer`（`dovetail/utils/ir_serializer.py`）已实现完整的 IR 序列化/反序列化，
   `BinarySerializer`（`dovetail/utils/binary_serializer.py`）提供字节流支持， 两者为 IR 级缓存奠定了基础，但尚未接入编译主流程。

4. **开发体验差**  
   频繁修改代码时，编译等待时间累积明显。

### 需求分析

- 开发者需求：快速验证代码修改效果
- 大型项目需求：支持模块化增量编译

## 技术规范

### 1. 缓存分层

本提案采用两层缓存策略，各层独立失效、独立存储：

| 层级        | 缓存内容                                     | 文件后缀 | 存放位置             |
|-------------|----------------------------------------------|----------|----------------------|
| L1 AST 缓存 | Lark `Tree` 对象（pickle）                   | `.mcdc`  | 源文件同目录         |
| L2 IR 缓存  | IR 指令序列 + 符号表（`IRSymbolSerializer`） | `.mcdci` | `./.dovetail_cache/` |

---

### 2. 缓存文件命名

缓存文件与源文件同目录，后缀由 `config.py` 分别规定为`mcdc`和`mcdci`

**L1 AST 缓存**（已实现）：

```
source/foo.mcdl  →  source/foo.mcdc
```

**L2 IR 缓存**（本提案）：

```
source/foo.mcdl  →  source/foo.mcdci
```

---

### 3. L1 AST 缓存规范

#### 3.1 设计动机

AST（Lark `Tree` 对象）是编译流水线中最早产生的中间产物，其特点是：

- **无外部依赖**：纯粹的树形结构，不含符号表、作用域等上下文信息，天然可序列化
- **生成代价固定**：每次解析都要跑完整的 LALR 状态机，对大文件耗时可观
- **失效条件简单**：只依赖源文件内容与语法文件，失效判断极低开销

#### 3.2 缓存文件格式

`.mcdc` 文件为 pickle 二进制文件，包含以下字段：

```python
{
    "grammar_hash": str,  # lark/dovetail.lark 全文内容的 MD5（32位十六进制）
    "file_hash": str,  # 源文件内容的 MD5（32位十六进制）
    "start": str,  # 解析起点，如 "program" 或 "expr"
    "tree": Tree,  # 序列化的 Lark Tree 对象
}
```

字段说明：

- `grammar_hash`：语法文件的 MD5，在 **模块加载时计算一次**并常驻内存，避免每次解析重复 I/O
- `file_hash`：源文件内容的 MD5，在读取文件内容后立即计算；MD5 碰撞概率在此场景下可忽略
- `start`：同一源文件可能以不同起点解析（`program` / `expr`），须纳入 key 以防混用
- `tree`：使用 `pickle.HIGHEST_PROTOCOL` 序列化，兼顾性能与兼容性

#### 3.3 缓存失效条件

| 条件           | 检测方式                                      |
|----------------|-----------------------------------------------|
| 源文件内容变化 | `file_hash`（MD5）不匹配                      |
| 语法文件变化   | `grammar_hash`（MD5）不匹配                   |
| 解析起点变化   | `start` 字段不匹配                            |
| 缓存文件损坏   | pickle 反序列化异常，静默忽略，回退到全量解析 |

> **不**将 `compiler_version` 纳入 L1 失效条件：AST 结构与编译器版本无关，
> 仅取决于语法文件

#### 3.4 读写流程

```
parser_file(filepath) 被调用
    │
    ├─ 文件合法性检查（存在、大小）
    │
    ├─ 读取源文件内容，计算 file_hash（MD5）
    │
    ├─ 尝试读取 filepath.with_suffix(".mcdc")
    │     ├─ 存在且字段全部匹配 → 反序列化 tree，直接返回       [缓存命中]
    │     └─ 不存在 / 字段不匹配 / 解码异常 → 继续              [缓存失效]
    │
    ├─ lark_parser.parse(code, start=parse_start)              [全量解析]
    │
    └─ 将 {grammar_hash, file_hash, start, tree} 写入 .mcdc    [写回缓存]
          └─ 写入失败（磁盘满、权限不足等）→ 静默忽略，不影响主流程
```

#### 3.5 注意事项

- `.mcdc` 文件应加入 `.gitignore`，避免提交进版本库
- pickle 格式与 Python 版本强绑定；若跨 Python 版本使用，旧缓存可能反序列化失败， 已由"静默忽略并回退"机制覆盖，无需额外处理

### 4. L2 IR 缓存规范

#### 4.1 缓存元数据结构

每个 `.mcdci` 文件由两部分组成： **元数据头**（JSON）+ **IR 字节流**（binary）。

元数据头：

```json
{
  "compiler_version": "1.0.2",
  "source_hash": "sha256:<64位十六进制>",
  "grammar_hash": "sha256:<64位十六进制>",
  "compile_config": {
    "namespace": "my_pack",
    "optimization_level": 2,
    "minecraft_version": "1.21",
    "debug": false,
    "recursion": false,
    "first_class_functions": false,
    "experimental": false
  },
  "dependencies": [
    {
      "path": "lib/std.mcdl",
      "source_hash": "sha256:..."
    }
  ],
  "timestamp": "2026-02-04T10:00:00"
}
```

字段说明：

- `compiler_version`：来自 `config.py` 中的 `PROJECT_VERSION`，版本升级时全量失效
- `source_hash`：源文件内容的 SHA-256，内容变更时失效
- `grammar_hash`：`lark/dovetail.lark` 的 SHA-256，语法变更时失效（复用 L1 缓存中已计算的值）
- `compile_config`：对应 `CompileConfig` 所有字段的序列化；任意编译选项变更均触发失效
- `dependencies`：由 `IncludeManager.get_included_paths()` 提供；任意依赖文件变更均触发级联失效
- `timestamp`：写入时间，仅供调试，不参与失效判断

---

#### 4.2 缓存失效条件

触发重新编译（缓存失效）的完整条件：

| 条件             | 检测方式                                         |
|------------------|--------------------------------------------------|
| 源文件内容变化   | SHA-256 哈希对比                                 |
| 语法文件变化     | `lark/dovetail.lark` SHA-256 对比                |
| 任意依赖文件变化 | 遍历 `dependencies` 列表，逐一对比 SHA-256       |
| 编译选项变化     | `CompileConfig` 全字段对比                       |
| 编译器版本变化   | `PROJECT_VERSION` 字符串对比                     |
| 用户显式清除缓存 | `--clean` CLI 参数，删除 `.dovetail_cache/` 目录 |

> **依赖追踪说明**：`IncludeManager` 在编译期间已维护完整的 `_include_history`，
> 通过 `get_included_paths()` 可直接获取当前文件的所有依赖路径，
> 无需额外的依赖图分析步骤。

---

#### 4.3 增量编译流程

```
编译开始
    │
    ▼
解析项目依赖图（IncludeManager）
    │
    ▼
对每个源文件：
  ├─ 计算文件 SHA-256
  ├─ 读取 .mcdci 元数据头
  ├─ 校验所有失效条件
  │     ├─ 命中缓存 → 反序列化 IR（IRSymbolSerializer.restore()）
  │     └─ 缓存失效 → 走完整编译流水线（解析 → IR 构建 → 优化）→ 写回 .mcdci
    │
    ▼
合并所有模块 IR
    │
    ▼
执行全局优化 Pass（optimize/pipeline.py）
    │
    ▼
后端代码生成（backend/）
```
